    *** ユーザー管理システム (Laravel API) ***

1. プロジェクト概要
    - 目標：Laravel のベストプラクティスに基づいた再設計。
    - 重点：より保守性の高いアーキテクチャの構築。

2. アーキテクチャ設計指針
    - 「Thin Controller / Fat Service」の原則を採用し、各コンポーネントの責務を明確に分離しています。
    - Controller: リクエストの受付とレスポンスの返却のみを担当。ビジネスロジックは一切持ちません。
    - Request: バリデーションとデータのクレンジングをカプセル化。
    - Service: ビジネスロジックの中核。データベース操作や外部連携（CSV出力等）を担当
    - Model: Eloquentを採用し、データ構造、リレーション、およびクエリスコープ・アクセサを定義。(database.txt)
        - **Single Responsibility**: 各レイヤーが単一の責務を持つことで、将来的な仕様変更に柔軟に対応できる構成としています。
        - **Eloquent Optimization**:
            - **Scopes**: 姓名連結検索などの複雑なクエリをモデル内にカプセル化し、Serviceレイヤーの可読性と再利用性を向上。
            - **Accessors**: `full_name` などの仮想カラムを定義し、ビューや CSV 出力におけるロジックの重複を排除。

3. ディレクトリ構成 (FileTree.md)
   app/
   ├── Http/
   │ ├── Controllers/ # リクエストの制御 (Entry Point)
   │ └── Requests/ # バリデーション (Security Layer)
   ├── Services/ # ビジネスロジック (Worker Layer)
   └── Models/ # データ構造とリレーション (Data Layer)

4. リクエスト処理フロー
    - Request(バリデーション実行)
    - Controller(Serviceメソッドの呼び出し)
    - Service(クエリ構築・ビジネスロジック実行)
    - Model(Eloquent)
    - Response(nextJS)

5. 主要機能の実装ポイント
    - ### 5.1
        - 検索ロジックの共通化 - UserSearchService 内に buildSearchQuery メソッドを設け、画面表示用の検索とCSVエクスポート用の検索で同一のクエリ構築ロジックを再利用しています。これにより、検索条件の変更に強い設計にしています。

    - ### 5.2 大容量 CSV エクスポート
        - メモリ効率を考慮し、StreamedResponse と Eloquent の chunk() メソッドを組み合わせて実装しました。
        - 大容量データ出力時でもサーバーメモリの消費を最小限に抑えます。
        - 文字コード：Excel でシームレスに表示できるよう、SJIS-WIN に変換されます。
        - 大量データ出力時の安定性を検証するため、17.5万件のレコードを使用してメモリ消費量を計測しました。
          **実装手法**: `StreamedResponse` + `Chunk`
          **計測結果**:
          開始時メモリ: **18 MB**
          ピーク時メモリ: **24 MB**
          実消費量: **わずか 6 MB**
          **結論**:
          データを一括で読み込まず逐次処理（Streaming）を行うことで、データ量に依存しない一定のメモリ消費量での出力を実現しました。

    - ### 5.3 論理削除の実装
        - 専用の t_user_delete テーブルへの記録方式を採用しています。削除履歴を物理的に分離管理する設計要件です。

    - ### 5.4 フロントエンド設計
        - ステートレスAPI: サーバーはセッション状態（Blade/Session）を保存しません。Next.jsとのすべてのやり取りはRESTリクエストを介して行われます。
        - JSON標準: すべてのレスポンスは厳密に型指定され、JSON 形式で返されるため、Next.js 側で TypeScript とのシームレスなやり取りが保証されます。
        - 関心の分離: 表示ロジック（フォーム、テーブル、モーダル）は React コンポーネントに完全に移行されています。データの一貫性とビジネスルールは Laravel が単独で責任を負います。　

6. バリデーション設計
    - CakePHPではTablesクラスにバリデーションを記述する傾向がありますが、本プロジェクトではLaravelのRequestを採用しました。これにより、コントローラーが肥大化するのを防ぎ、再利用性とテストのしやすさを向上させています。

7. 結論
    - 本リプレイスでは、CakePHP の既存仕様を尊重しつつ、Laravelの特性を活かした、保守性の高い構成を目指しました。

8. 最適化と投入
    - ### 8.1.　テストデータ生成
        - システムは Factory と Seeder を使用して生成されます。(TUserFactory.php/TUserBelongsFactory.php)
        - ローカライズ：データは日本語（ja_JP）で生成されます。
        - 整合性：シーケンスを使用することで、ID とメールアドレスの重複を排除します。
        - 効率性：静的パスワードハッシュにより、シード処理が大幅に高速化されます。

    - ### 8.2. パフォーマンス

        本システムは Next.js フロントエンドと連携するステートレス API として構築されています。
        開発中、175,000 件を超えるデータを対象とした検索処理において、レスポンス遅延が発生しました。
        - 課題
          本システムでは offset-based pagination を採用しています
          インデックスを利用しないソートによるフルスキャン発生

        - 改善内容
          ソート対象をインデックス付き user_id（主キー）へ変更
          クエリ最適化（不要カラムの削減）
          CSV出力時に chunk() + StreamedResponse を採用

        - 結果
          APIレスポンス時間：38秒 → ~0.5秒
          大規模データ環境下でも安定した応答性能を確保

        ※ APIレベルでのクエリ最適化と、フロントエンド側での描画制御を分離して改善。
